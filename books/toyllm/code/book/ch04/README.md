# 第四章 · 词嵌入（Embedding）

这一章第一次真的从 `model.safetensors` 里取数据，而且只取一个张量：
`model.embed_tokens.weight`，形状 49152 × 576，28,311,552 个参数，占全模型的 21%。

第三章停在一串 ID，这一章把 ID 换成向量。形状上就是 `(T,) → (T, 576)`。

## 运行

```bash
cd code
./download_model.sh                                  # 还没下权重的话，先跑这个
uv run python book/ch04/embed_demo.py                # 文字 → 词元 → ID → 向量
uv run python book/ch04/embed_demo.py "任意一段话"
uv run python book/ch04/model.py                     # 一个矩阵两个方向，每个位置各预测一个词
uv run python book/ch04/engine.py                    # 两头真算，中间空着，转 10 圈
uv run python book/ch04/vocab_head.py                # 词表开头 10 行，输出是张 Markdown 表
```

## 文件

| 文件 | 作用 |
|---|---|
| `embed_demo.py` | 给一段文字，打印词元、ID，以及每个 ID 查出来的那个 576 维向量，并标出形状变化 |
| `model.py` | `Model` 类：`to_embeddings` 查表，`to_logits` 投影，`forward` 把两头接起来；单独跑只演示两个方向 |
| `engine.py` | `Engine` 类：Tokenizer + Model + 贪婪采样 + Detokenizer；`generate` 是 ID 进 ID 出，转 10 圈 |
| `weights.py` | 第二章那个 `Weights` 类，一字未改搬过来，`Model` 用的就是它 |
| `vocab_head.py` | 不给文字，直接从词表第 0 行往下看，前 10 个词元、ID 和向量，排成 Markdown 表格 |

## 查表就是取行

`Model` 的两个方向，各只有一行代码：

```python
def to_embeddings(self, ids):        # (T,)       → (T, 576)
    return self.weights.embed_tokens[ids]

def to_logits(self, x):              # (..., 576) → (..., 49152)
    return x @ self.weights.embed_tokens.T
```

入口没有矩阵乘法，只是按行号取行，token 6403 的向量就是矩阵的第 6403 行。出口才是
一次真的矩阵乘法：和词表里每一行做点积，谁像谁得分高。两个方向用的是同一份权重，
所以文件里找不到 `lm_head.weight`。

`to_embeddings` 只收一串 ID，哪怕只有一个词元也要写成 `[id]`，出来的永远是 T 行，
这样整条流水线上的形状只有一种说法。

## model.py 的输出

`model.py` 单独跑只做一件事，把两个方向各走一遍，不生成文字，生成那件事归 `engine.py`：

```
文字     'Once upon a time'
ID       [6403, 1980, 253, 655]
形状     (4,) → (4, 576) → (4, 49152)

每个位置各自预测下一个词元：

  第0个  'Once'       → 'Once'
  第1个  'Ġupon'      → 'Ġupon'
  第2个  'Ġa'         → 'Ġa'
  第3个  'Ġtime'      → 'Ġtime'
```

这里喂给 `to_logits` 的是整个 `(4, 576)`，4 个位置各出一行分数，所以形状那行是
`(4,) → (4, 576) → (4, 49152)`，全章只有这一处是批量投影。`engine.py` 走的是
`forward`，只投影最后一行，出来的是 `(49152,)`。

每个位置都预测出自己，这是「上下文还不存在」最省字的说法：没有任何东西把别的位置混
进来，第 3 个位置压根看不见前面的 `Once upon a`。

## 两种加载方式

`Model` 用的是第二章那个 `Weights`，一次把 272 块全读进来，fp32 之后约 538 MB。

`embed_demo.py` 没走这条路，而是自己 `safe_open` 只取 `model.embed_tokens.weight`
一块：文件里它占 56,623,104 字节（bf16），升成 fp32 之后翻一倍，其余 271 个张量一个
都没碰。留着这个对照，是因为 `safe_open` 按需读这件事本身值得看一眼。

两边都在加载时统一升成 fp32，和全书其他章节一致：CPU 上 fp32 的算子更快也更全。

`ch04/weights.py` 和 `ch02/weights.py` 逐字节相同。每一章的目录都是上一章的完整
副本，所以从这一章起，它会一直跟着走下去。

## engine.py 的输出

`Engine` 把四个模块凑齐了：Tokenizer、LLM、Sampler（这一章就是取最高分的贪婪采样）、
Detokenizer。转 10 圈，每圈把新词元追加到序列末尾，然后整串重算一遍。

`generate` 只管 ID 进 ID 出，打印留给 `main`，而且输入和生成摆在同一张表里：对引擎来说
这两者没有任何区别，都是 ID，都在同一张表里查同一行，分开打印反而会把这件事说拧。

## 为什么一直在重复最后一个词

因为中间是空的，**最后那个位置的向量，就是词表里 `Ġtime` 那一行本身**，没有任何一层
碰过它。

出口问的是「词表里哪一行和这个向量点积最大」。拿自己去问，自己和自己的点积就是模长
平方：

```
Ġtime 的模长 2.894，模长平方 8.378

   8.378  'Ġtime'      ← 自己
   5.491  'time'
   5.165  'ĠTime'
   4.847  'Ġtimes'
```

第二名差了将近三分，所以选中的就是它自己。选完追加到末尾，`forward` 又只看最后一行，
状态和上一圈一模一样，于是永远循环下去。用数学的话说，`Ġtime` 是这个映射的一个
不动点。

两件事顺带看清楚了。

**一、前面的 `Once upon a` 一个字都没参与。** 没有任何东西把它们混进最后那个向量里，
而「把别的位置混进来」正是注意力机制要干的活（第六章）。所以现在这个引擎连上下文这
个概念都还没有，更别说词序了。

**二、不是所有词都复读自己，但都会卡住。** 反复迭代几步看看：

```
'Hello' → '<filename>' → '<filename>' → ...
'veh'   → 'Ġstrugg'    → 'Ġstrugg'    → ...
```

`Hello` 的模长只有 2.6，守不住自己，被模长 6.7 的 `<filename>` 抢走；`veh` 被模长
7.47（在 49152 行里排第一）的 `Ġstrugg` 抢走。但抢走之后照样卡死，因为这个映射是
确定的，迭代下去必然落进某个不动点或者小循环。

说到底就一句话：**点积 = 模长 × 余弦**，模长大的那一行总占便宜。这两件事正好指向后面
两章，第五章的 RMSNorm 管的是模长那条腿，第六章的注意力管的是把上下文混进来。

## 模长为什么是 2 到 3

表里的模长挤在 3 附近，全表 49152 行也一样：中位数 3.13，1% 分位 2.13，99% 分位
4.93，最小 1.757，最大 7.468。这不是巧合，但也不神秘。

**一、大头是维度贡献的。** 模长 ≈ √576 × 每个分量的典型大小 = 24 × 0.135 ≈ 3.2。
单个分量其实很小，是 576 这个维度把它撑到了个位数。

**二、初始化的模长正好是 1.000。** `config.json` 里 `initializer_range` 写着
0.041666...，也就是 1/24 = 1/√576，这个值就是为了让初始的每一行都是单位长度。所以
2 到 3 这个量级是训出来的，训练把它们从 1 撑到了 2 至 5。

**三、撑到哪由出口决定。** `model.norm.weight` 均值 1.791，隐状态过完最后那个
RMSNorm，模长大约 √576 × 1.791 ≈ 43，再乘上词向量模长 3.13，就是 logit 的量级。
词嵌入模长和 `model.norm.weight` 是一对耦合的旋钮，两边一起把 logit 顶到 softmax
用得动的范围里。所以单看词嵌入模长是多少，并没有绝对意义。

**四、ID 5、7、8、9 那四行不是「没训过」。** 它们看着几乎一样，两两余弦是
1.0000，而 576 维里两个独立随机初始化的向量，余弦应该接近 0。它们不是没动过，是被
训到一起去了：`tie_word_embeddings` 让每一行同时是 `lm_head` 的一行，于是每一步训练，
softmax 的分母都会给全部 49152 行一个往下压的梯度。从没当过目标的那几个词元只挨压、
从不挨拉，就一起漂到了同一个地方（和全表均值向量的余弦 0.878）。

**五、高频词的模长反而小。** byte-level BPE 的 ID 大致按合并次序排，小 ID 就是高频
词元：

| ID 区间 | 模长中位数 |
|---|---|
| 0–6143 | 2.636 |
| 12288–18431 | 2.879 |
| 24576–30719 | 3.180 |
| 36864–43007 | 3.392 |
| 43008–49151 | 3.496 |

这个趋势很干净，成因有好几种说法，这里只摆现象。

这一节的数字是临时探查出来的，ch04 的脚本里只留了 `vocab_head.py` 那一列模长。要复算
的话，全表模长是 `embed.norm(dim=1)`，分位数用 `torch.quantile`，余弦用
`torch.cosine_similarity`，`initializer_range` 在 `config.json` 里。

## 引擎现状

两头都通了：`ids → embed → lm_head → logits`，用的是同一个矩阵，正着读一遍、
反着读一遍。SmolLM2 的 `tie_word_embeddings` 是 `true`，所以 `model.safetensors`
里根本找不到 `lm_head.weight`（第二章那个疑问，答案就在这里）。

中间那 30 层还是空的，所以输出仍然是胡言乱语，只是胡得和第三章不一样了：第三章是
随机数决定的，这一章是模长决定的。
