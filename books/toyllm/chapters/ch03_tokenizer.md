**数据在图上换了好几种形态。**

```
文字 → tokens → token ids → 向量 → logits → 概率 → 新的 token id → 新的 token → 文字
你好吗   你 好 吗    9 5 2     x₁x₂x₃    49152个数   49152个概率      7            ？        ？我很好…
```

左右两端是"字"的世界，中间是"数"的世界。Tokenizer 和 Detokenizer 是这两个世界的边境口岸，而且它们互为镜像——一个把字翻成数，一个把数翻回字。

Tokenizer 分两步：**Tokenization**（把文字切成 token）和 **Token-to-ID Mapping**（查表把 token 换成整数）。图上「你好吗」被切成「你 / 好 / 吗」，再查表得到 `9 5 2`。Detokenizer 是完全对称的两步反向操作。

要讲清楚的几点：

- **为什么要分词**：模型只会做矩阵运算，只认数字。文字必须先变成整数。
- **为什么切成 token 而不是字或词**：按字符切，词表小但序列太长；按词切，词表爆炸还处理不了新词。token 是二者之间的折中——常见词一个 token，生僻词拆成几个。SmolLM2 的词表是 49152 个。
- **这两个盒子里没有一个浮点数**。没有权重，没有矩阵乘法，只有一张表和一套切分规则。本章会看到：做分词根本不需要打开那个 269 MB 的权重文件，词表在另一个文件 `tokenizer.json` 里。
- **生成侧是一个一个吐的**。图里 Generated Tokens 那几个虚线框说明了这一点，这给 Detokenization 留了个坑——一个汉字占 3 个字节，可能被切进两个 token，逐个解码会出乱码。



## 分词



### 为什么需要分词

模型只会做矩阵乘法，只认整数下标。任何文字都必须先变成一串整数，它才有得算。

怎么切，有三条路：

| 切法 | 词表 | 序列长度 | 问题 |
|---|---|---|---|
| 按字符 | 小（几千） | 很长 | 依赖距离拉长，模型难学 |
| 按词 | 巨大 | 短 | 词表爆炸，遇到新词抓瞎（OOV） |
| **按子词** | 中等 | 中等 | 常见词整块，生僻词拆开，无 OOV |

现代模型全走第三条路。SmolLM2 的词表是 **49152** 个 token。



### BPE：怎么来的，怎么用的

BPE（Byte Pair Encoding）本来是个压缩算法，被借来做分词。

**训练时**（不是我们要做的事，但要讲清楚，否则合并表看着像天书）：从最小单位开始，反复统计哪一对相邻符号出现得最频繁，把它合并成一个新符号，记进 merges 表。跑几万轮，就得到了词表和一张有先后顺序的合并表。高频的组合先被合并，所以它们在表里靠前。

**推理时**（我们要写的）：把文本拆成最小单位，然后**按 merges 表的顺序**反复扫描、合并。注意合并是有优先级的——merges 表里的先后顺序就是优先级，谁先合并结果完全不同。



### byte-level 是什么意思

不是从字符开始，是从**字节**开始。

任何文本都能拆成 UTF-8 字节，字节只有 256 种，所以**永远不会有 OOV**——再生僻的字、emoji、乱码，都能编码。代价是一个汉字要占 3 个字节，中文的 token 效率天然比英文低。

实现上有个小花招：字节 0-255 里有很多不可打印字符，直接当字符串处理很麻烦，所以 byte-level 把它们映射到一批可打印字符上（空格变成 `Ġ` 就是这么来的）。



### SmolLM2 的完整管线

```
Digits(individual_digits) → ByteLevel(use_regex) → BPE
```

没有 normalizer，没有 post-processor。三段各干一件事：

- **Digits**：数字逐位切开，`2024` → `2` `0` `2` `4`。不这么做，模型很难学会数字之间的关系
- **ByteLevel**：先用一段正则做预切分（把空格、标点、字母分组），再把字节映射到可打印字符
- **BPE**：按合并表反复合并

**没有 post-processor 意味着不会自动加 BOS/EOS。** 加不加、加什么，是调用方的决定。这一点在第十章做对话模板时会再遇到。

### 三个静默错误

这一章最值得写的部分。这三个错误都**不会报错**，只是 token id 悄悄不对，然后模型输出莫名其妙地变差：

**一、数字判定的边界。** `Digits` 判断一个字符是不是数字，要用 `unicodedata.category(ch)[0] == "N"`，对齐 Rust 的 `char::is_numeric()`（涵盖 Nd/Nl/No 三类）。Python 的 `isdigit()` 太窄，漏掉 `½`；`isnumeric()` 又太宽，会把汉字「一」也算成数字（它其实是 Lo 类）。

**二、别自作主张加 BOS。** 上面说了没有 post-processor。见过的模型都自动加 BOS，这个就不加，照着 config 来。

**三、21 个字节 token 不在词表里。** 256 个字节里有 21 个在这个词表中找不到对应 token，其中 8 个（`0x04 0x06 0x13 0x14 0x16 0x1D` 以及 `0xF1 0xF2`）从普通字符串里就能碰到。HF 的处理方式是**静默丢弃**，所以 `"a\x04b"` 编码出来是 `["a", "b"]`。

我们要**照抄这个行为**。"修好"它会产生模型训练时从没见过的 id，那才是真的坏了。

由第三点得到一个反直觉的结论：**byte-level BPE 号称无损，但这个词表其实不是。** encode 之后再 decode，不保证拿回原文。



## 反分词（Detokenizer）

反过来走：`id → token 字符串 → 字节 → UTF-8 解码`。ByteLevel 那套字符映射要反着做一遍。

看起来只是把上面倒过来，但有两件事只在这个方向上出现。



### 空格去哪了

byte-level 把空格编码成了 `Ġ`，所以 `"Hello world"` 的第二个 token 是 `"Ġworld"` 而不是 `"world"`。这解释了为什么直接打印 token 列表会看到一堆奇怪符号——它们不是乱码，是空格。decode 时要还原回去。

顺带说明一个常见困惑：`"world"` 和 `"Ġworld"` 是**两个不同的 token**，有各自的 id 和各自的词向量。词首和词中的同一个词，在模型眼里不是一回事。



### 流式输出的坑

这是本节最重要的内容。

生成是**一个一个 token 出来的**（看图上 Generated Tokens 那几个虚线框）。想做打字机效果，就得每拿到一个 token 就 decode 一次、立刻打印。

问题是：一个汉字占 3 个 UTF-8 字节，完全可能被切进两个 token。单独 decode 其中任何一个，得到的都是 `�`。

正确做法是维护一个**字节缓冲**：每个 token 解出来的字节先进缓冲，凑齐完整的 UTF-8 字符再输出，凑不齐就等下一个 token。

值得强调的是，**这个坑只在推理时存在**。训练视角的书遇不到它，因为它们只在最后整段 decode 一次。这类"只有真跑起来才会撞上"的问题，正是这本书想讲的东西。

第十章做流式输出时，这个雷会真的响。



## 本章小节

这一章做完了第一章总览图最外侧的两个盒子：

- Tokenizer：文字 → tokens → ids，和 `tokenizers` 库逐个整数相等
- Detokenizer：ids → tokens → 文字，包括流式所需的字节缓冲

也发现了两件和常识相左的事：这个词表的编码**不是无损的**；流式解码**不能逐 token 做**。

引擎现在的样子：**两端通了，中间是空的**。我们能把「你好吗」变成 `9 5 2`，也能把 `7` 变回文字，但从 `9 5 2` 到 `7` 那一步还完全不存在。
