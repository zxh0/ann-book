# KV Cache

> **本章代码**：上一章接通的那个循环，每一轮都在重算全部历史。这一章把它治好。
>
> - **造哪个框**：**不新增任何框**。改的是那条 `append to` 虚线怎么走
> - **关键**：推理从此裂成两段——**prefill**（一次吃完整段 prompt）和 **decode**（每次只算一个新 token）。历史 token 的 K、V 每轮都完全相同，存下来就是了
> - **形状**：decode 阶段输入从 `(T, 576)` 缩成 `(1, 576)`，K/V 从缓存里取
> - **跑出什么**：**全书唯一可以正当谈性能的一章**——加速比，以及缓存内存随长度的增长曲线。第六章那个 9 q 头 / 3 kv 头的设计在这里才兑现价值：8192 上下文下 378 MB vs 1133 MB
> - **对拍**：判据是 `torch.equal` 而**不是**容差。解码是一连串 argmax 决策，缓存错一个位置，文本会整段跑偏而不是数值微抖
> - **坑**：key 要存 **RoPE 之后**的，否则历史会被反复旋转；续写时 `positions` 从 `cache.length` 起算而不是 0（错了不报错，只是 RoPE 编码出错误的距离）；30 层共用一个偏移，全部写完才 advance 一次

前十章的问题都是"算得对不对"。从这一章开始，问题变成"算得快不快"——但对正确性的要求反而更严。

这一章不新增任何部件。第一章总览图上不会多出一个框，因为它改的不是数据流，是**同一条数据流的执行方式**。



**先回到第一章那张总览图，看右下角那条虚线。**

标着 `append to` 的那条虚线，从 Generated Token IDs 绕回到 **Token IDs**——注意不是绕回 Text。这一条线包含了三个事实：

- 模型一次只产出**一个** token。图里 LLM 输出了好几个向量，但只有最后一个用来预测下一个词。
- 想要第二个 token，就得把刚生成的那个接到 id 序列末尾，**整条流水线从头再走一遍**。
- 于是生成第 n 个 token 时，前面 n-1 个 token 全部要重新计算。这是纯粹的浪费，也是本章 KV Cache 存在的全部理由。



## 慢在哪里

### 把浪费算出来

上一章的生成循环是这样的：生成第 $n$ 个 token 时，把 1..n-1 全部重新 forward 一遍。

生成 100 个 token 的总计算量：

$$1 + 2 + \cdots + 100 = 5050$$

而理论上只需要算 100 个 token。**50 倍的浪费**，而且这个倍数随生成长度线性增长——生成 1000 个 token 就是 500 倍。

实测上表现为：每生成一个 token 的耗时**越来越长**。这条曲线值得实际跑出来画一下，它比任何论证都有说服力。

### 为什么是纯粹的浪费

关键在因果掩码。

第六章讲过，第 $i$ 个位置只能看 1..i。这意味着**在序列末尾追加一个新 token，不会改变前面任何一个位置的任何中间结果**——它们看不到新来的这个。

所以第 $n$ 轮算出来的前 $n-1$ 个位置的东西，和第 $n-1$ 轮**逐位相同**。重算一遍，得到的是一模一样的数。

这不是"可以优化的低效"，是**完全重复的劳动**。

### 该存什么

不是存 hidden states，是存每一层的 **K 和 V**。

因为新 token 需要的是：用自己的 $\mathbf{q}$ 和**所有历史的 $\mathbf{k}$ ** 做匹配，再从**所有历史的 $\mathbf{v}$ ** 里加权取值。 $\mathbf{q}$ 是新算的（只需要新 token 自己的），k 和 v 却要全套历史——那就把它们存下来。

这也解释了名字：KV Cache，缓存的正是 K 和 V。



## KV Cache

### 结构

每一层一个缓存，各存一份 K 和一份 V：

```
K: (已生成长度, 3, 64)
V: (已生成长度, 3, 64)
```

注意是 **3** 个 kv 头，不是 9 个——GQA 在这里兑现。

新 token 到来时：算出它自己的 q/k/v，把 k、v **追加**进缓存，然后拿 q 和整个缓存做注意力。

### 内存账

这笔账必须算给读者看，因为它是生产环境里最要命的数字。

```
每 token 每层  K + V = 2 × 3 × 64 = 384 个数
fp32          384 × 4 = 1,536 字节
30 层         1,536 × 30 = 46,080 字节 ≈ 45 KB / token
8192 上下文   45 KB × 8192 ≈ 378 MB
```

对比一下：如果不用 GQA、老老实实 9 个 kv 头，同样的算式得出 **1133 MB**。

第六章说过"GQA 省的不是参数，是 KV Cache"——就是这个 378 对 1133。参数只省了 44 万（0.3%），内存省了三分之二。**一个为推理而做的设计，在推理章才看得到它的价值。**

### 用内存换计算

要点破一句：KV Cache 的本质是**拿内存换计算**。

模型权重本身才 269 MB，而缓存在长上下文下能轻松超过它。生产环境里显存的大头往往不是模型，是 KV Cache——这也是 PagedAttention 那一整套技术存在的原因（后记里提）。

对我们的玩具引擎来说，知道这个量级关系就够了。



## Prefill 与 Decode

### 两个阶段

有了缓存，推理裂成性质完全不同的两段：

| | prefill | decode |
|---|---|---|
| 输入 | 整段 prompt，T 个 token | 1 个 token |
| 形状 | `(T, 576)` | `(1, 576)` |
| 缓存 | 从空到满 T | 每轮追加 1 |
| 矩阵 | 大矩阵乘法 | 矩阵 × 向量 |
| 瓶颈 | **计算** | **内存带宽** |
| 次数 | 1 次 | 每个输出 token 一次 |

### 为什么瓶颈不一样

这是本章最值得展开的一点。

**prefill 是计算密集的**：T 个 token 并行过一遍，矩阵够大，硬件利用率高。

**decode 是内存带宽密集的**：每次只算 1 个 token，计算量小得可怜——但为了算这一个 token，**必须把 269 MB 的权重完整读一遍**。算术强度极低，时间全花在搬数据上。

这个差异是现代推理引擎几乎所有复杂性的源头：两个阶段瓶颈不同，所以最优的批处理策略、调度策略都不一样。**PD 分离**（把 prefill 和 decode 放到不同实例上跑）就是从这里长出来的——不过那是服务架构，超出本书范围，后记里提一句即可。

对我们的引擎，只要能观察到一个现象就够了：**decode 阶段每一步的耗时基本恒定**，不再随已生成长度线性增长。

### 顺带一个小优化

decode 时 T = 1，因果掩码只有一行而且全是 0（能看到所有历史），**整个掩码可以跳过**。第六章埋的伏笔在这里收。



## 代码实现

### 缓存是一个开关，不是一条分支

先说设计。最自然的写法是到处判断：

```
if cache is not None:
    ...
else:
    ...
```

**不要这么写。** 一旦开始加分支，attention 的 forward 会分裂成两套逻辑，两套都要维护、都要测，而且很容易出现"带缓存和不带缓存行为不一致"的 bug——那恰恰是这一章最难查的错误。

更好的做法是做一个 `NoCache` 空对象：

- `update()` 把传进来的 k、v 原样返回
- `length` 恒为 0

于是所有的位置计算、掩码计算自动退化成无缓存的行为，模型代码里**一个 `if cache is not None` 都不需要**。默认参数就是 `NoCache`，要缓存时换成 `KVCache`。

和第十章 `GreedySampler` / `RandomSampler` 是同一个思路：**用策略对象替代运行时分支。**

### 三个坑

这三个都不报错，只是结果悄悄出错。

**一、存 RoPE 之后的 K。** 如果存旋转前的，每一轮都得把整个历史重新旋转一遍——白费计算不说，还极容易转错角度。存旋转后的，历史就永远不用再动。

**二、`positions` 要从 `cache.length` 起算，不是从 0。** 续写时新 token 的位置是第 `cache.length` 个。写成 0 不会报错，只是 RoPE 会按错误的距离编码，生成的文本莫名其妙地变差——这种"能跑但变笨"的 bug 最难查。

**三、30 层共用一个偏移。** 每一层都往同一个位置写 k、v，等 30 层全部写完之后，整体 `advance` 一次。如果在每层里 advance，后面 29 层就全错位了。

### 一个容易忽略的细节

`generate` 返回之后，缓存里只有 `len(output) - 1` 个 token——**最后那个 token 是从最后一次 forward 出来的，从来没被喂回模型**。

所以想接着上一轮继续生成（多轮对话就是这个场景），要从 `output[:, -1:]` 开始喂。这个 off-by-one 不注意就会漏掉或重复一个 token。

### 对拍：判据是 torch.equal

这一章的判据比前面几章都严，理由值得说清楚。

前面几章比的是浮点数值，允许 1e-6 的相对误差。**这一章不行，要 `torch.equal`。**

因为解码是一连串 argmax 决策。缓存写错一个位置，不会表现为"数值微抖"——而是某一步 argmax 选了另一个词，然后这个词进入下一轮输入，整段文本从此跑偏。**错误是离散的、放大的，不是连续的、衰减的。**

关键测试只有一条，但它能抓住几乎所有缓存 bug：

> **带缓存生成的结果 == 不带缓存生成的结果**，逐 token 相等。

因为不带缓存的那条路径在第八章已经和 transformers 逐字节对过了，它现在就是可信的基准。

### 性能

跑两条路径，打印耗时对比和加速比，再画一张"每 token 耗时 vs 已生成长度"的曲线：无缓存是一条向上的斜线，有缓存是一条平的。

这是全书唯一一次可以正当地谈性能。



## 本章小结

这一章没有新增任何部件，但引擎的性质变了：

- 因果掩码保证历史的 K、V 永不改变，所以可以缓存
- 推理裂成 **prefill**（计算密集）和 **decode**（内存带宽密集）两个阶段
- GQA 在这里兑现：378 MB 而不是 1133 MB
- 缓存做成**空对象**而不是 if 分支
- 判据回到 `torch.equal`——argmax 链容不得一点偏差

**「推理引擎」这四个字，从这一章开始才算名副其实。** 前面九章做的其实是"模型"，prefill/decode 这个划分才是引擎独有的东西。
