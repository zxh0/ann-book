# 前言

> TODO：书名待定。「引擎」二字是否名副其实，取决于最后一章交付什么——见「代码组织」。

这本书用 Python 和 PyTorch，从零手写一个能跑的 LLM 推理引擎：加载真实的模型权重，把一段文字变成 token，算完三十层 Transformer，采样出下一个词，再把它变回文字——然后循环。

全程不使用 `transformers` 的建模代码。分词、权重加载、RMSNorm、RoPE、GQA、SwiGLU、KV Cache、采样、生成循环，全部自己写。

目标模型是 **SmolLM2-135M**，跑在一台**普通笔记本的 CPU** 上。慢，但每一个数字都能和 HuggingFace 对上。



## 写作动机

一句话：

> 从训练入手，会比较难；从推理入手，就比较简单，然后再去学训练。
>
> 从 GPU 入手，会比较难；从 CPU 入手，就比较简单，然后再去学 GPU。

### 为什么是推理

「从零手写理解 LLM」这个赛道其实很挤——Karpathy 的 nanoGPT 和 llm.c、Raschka 的《Build a LLM from Scratch》（中译《从零构建大模型》）、以及无数篇「手写 Transformer」。

但它们几乎全是**训练视角**：搭一个模型，然后训练它。

从训练入手，你必须同时面对四件事：模型结构、反向传播、数据和训练技巧、以及漫长的等待。四件事纠缠在一起，任何一个环节出问题都很难定位。

从推理入手，只剩下一件事：**模型结构**。而且：

- **不用管梯度**。前向传播就是一串矩阵乘法，每一步都能打印出来看
- **不用管数据**。权重是现成的，别人已经训好了
- **不用等**。CPU 上一次前向是秒级的，改一行代码立刻能看到结果
- **每一步都可验证**。有 `transformers` 当参照，自己写的每个部件都能当场对答案

最后一条最关键。训练时你很难判断"我这么写对不对"——loss 在降就算对吗？而推理时，你的输出和参考实现要么逐位相同，要么就是错的。**这本书的整个方法论建立在这一点上。**

### 为什么是 CPU

同样的道理：GPU 会带来一整套与"理解 LLM"无关的麻烦——驱动、显存、CUDA 版本、租卡。而这些麻烦在真正理解模型结构之前，全都是噪音。

CPU 慢，但慢得清清楚楚。而且 135M 的模型在 CPU 上跑一次前向只要几秒，做实验完全够用。

等你理解了推理，再去看训练；等你理解了 CPU 上的实现，再去看 GPU 上为什么要那么写——那时候这两件事都会容易得多。**后记会给出这两条路怎么走。**

## 这本书不做什么

先把边界划清楚，免得期望错位。

**不是 vLLM。** 我们的目标不是写出一个能上生产的推理引擎，而是理解 LLM 的工作原理——更准确地说，是理解它的推理过程。连续批处理、PagedAttention、分布式调度，这些都不在范围内（后记会提一句它们在解决什么）。

**不讲训练，也不讲反向传播。** 这是一条硬约定，下面「阅读约定」会正式写出来。

**不追求效率。** 能工作即可。唯一的例外是第十一章——KV Cache 本身就是一个性能问题，不谈性能就讲不清它为什么存在。除此之外，全书一律选"看得懂"而不是"跑得快"。

**只解释 how，不解释 why。** 很多设计（比如 SwiGLU 为什么比 ReLU 好）连提出它的论文作者都说不清楚。遇到这种情况，本书会如实说明「它能工作，机理不明」，而不是硬编一个理由。



## 目标读者

**略懂 AI、DL、ANN、LLM，想再往里走一层，但一见到微积分和反向传播就想跳过的人。**

或者：只想从推理的角度把 LLM 搞明白的人。

具体一点：

- **要会写代码**，所以这本书不是给零基础的人看的
- **可以不懂 PyTorch**。它只是工具，不是重点，用到什么讲什么
- **可以不记得线性代数细节**。矩阵乘法和点积当作已知，其余用到时现讲
- **不需要懂微积分和反向传播**。全书用不到



## 阅读约定

三条贯穿全书的规矩，先说在前面。

**一、凡是要靠反向传播才能解释的问题，本书只给结果。**

比如「为什么残差连接是必要的」「为什么 pre-norm 比 post-norm 好」，标准答案都在梯度里。本书会告诉你结论、以及它对推理代码的影响（比如 pre-norm 导致模型末尾必须多一个 norm），但不展开原因。

想知道为什么，那是训练的事——也正是这本书希望你之后再去学的东西。

**二、每一章都和 transformers 对拍。**

书里每写完一个模块，我们都会拿它和transformers算出来的结果比一比，看看数字对不对得上。

能要求的精度是逐章下降的。前几章可以要求两边逐位相同，一个比特都不差；等第七章位置编码进来，就只能比相对误差了，第七章会专门解释为什么。

你不需要信我，跑一遍就知道。

**三、盯住形状。**

这本书里绝大多数 bug 不是数学错误，是形状错误——转置了、维度顺序反了、reshape 拼错了。所以正文里凡是有形状变化的地方，都会把前后的形状写出来，比如 `(T, 576) → (T, 9, 64) → (T, 576)`。

这类错误有个共同特点：**不报错**。代码照跑，输出也像模像样，只是全错。这也是第二条约定存在的理由。



## 技术选型

**编程语言：Python 3.12。** AI 领域的事实标准，没什么好讨论的。

**框架：PyTorch 2.2。** 只用它的张量运算（矩阵乘法、广播、`nn.Linear` 这类基础设施），不用它的任何高层封装。选 PyTorch 而不是 NumPy，是因为权重文件、参考实现、社区生态都在这边；卡在 2.2 这个版本，是因为作者的 MacBook 是 Intel 芯片，PyTorch 从 2.3 起不再发布 macOS x86_64 的安装包。



### SmolLM2

**模型：SmolLM2-135M。** 三个理由：

1. **架构够现代**。它是 Llama 架构的 decoder-only 模型，RMSNorm、RoPE、GQA、SwiGLU、权重共享一应俱全。学会它，主流模型的结构就都认识了
2. **够小**。1.35 亿参数，权重 269 MB，笔记本 CPU 上跑一次前向是秒级
3. **数字算得清**。全书会反复手算参数量和张量形状，135M 的每个数都能心算验证

和几个常见选项比一下（**具体数字待核实**）：

| 模型             | 规模     | 架构世代                                  | CPU 上         |
| ---------------- | -------- | ----------------------------------------- | -------------- |
| GPT-2 small      | 124M     | 旧（LayerNorm + 绝对位置编码 + 普通 FFN） | 能跑           |
| **SmolLM2-135M** | **135M** | **新**                                    | **能跑，秒级** |
| Llama 3.2-1B     | ~1.2B    | 新                                        | 勉强，体感差   |
| Qwen2.5-1.5B     | ~1.5B    | 新                                        | 勉强，体感差   |

GPT-2 够小但太老，学到的东西过时；1B 级别的模型架构对但太大。SmolLM2-135M 是「够新」和「够小」的交点。



SmolLM2是HuggingFace在2024年10月放出的小模型系列，论文见 https://arxiv.org/abs/2502.02737 。有135M、360M、1.7B三个尺寸，**本书全程用最小的135M**。

选它的理由有三条：

1. **架构是现代标配**。它是 Llama 架构的 decoder-only 模型（HF 里就叫 `LlamaForCausalLM`），RMSNorm、RoPE、GQA、SwiGLU、权重共享一样不缺。学会它，Llama 3.2、Qwen 2.5 这些主流模型的结构就都认识了。
2. **小到笔记本能跑**。1.35 亿参数，权重文件 269 MB，全部升成 fp32 装进内存也只有 1 GB 出头，CPU 上跑一次前向是秒级的。
3. **数字算得清**。全书会反复手算参数量和张量形状，135M 的每一个数都能心算验证。

对比一下常见的几个小模型：Llama 3.2-1B 和 Qwen 2.5-1.5B 架构类似但大一个数量级，CPU 上跑起来体感很差；GPT-2 倒是够小，但它用的是 LayerNorm + 绝对位置编码 + 普通 FFN，全是上一代的东西。SmolLM2-135M 是"够现代"和"够小"的交点。

这个系列一共出过三代：2024年7月的SmolLM，2024年10月的SmolLM2，2025年7月的SmolLM3。用第二代而不是最新的第三代，是因为SmolLM3只有3B一个尺寸，对本书来说有三处不合适：权重被切成了两个文件，本章要讲的“一个文件、一段索引、一片浮点数”这个干净结构就没了；它的`model_type`已经不是`llama`，每隔四层有一层不加位置编码，第七章要多讲一套东西；词表也涨到了128256，光一个词嵌入矩阵就有2.6亿个参数，差不多是整个SmolLM2-135M的两倍。



## 代码组织

**每章一个目录，逐章增量。**

```
code/
  models/      模型权重，所有章节共享（很大，不入库）
  reference/   第一章生成的基准输出，所有章节共享
  ch01/
  ch02/        复制 ch01，增量修改
  ...
  ch11/        最终形态
```

每一章的目录都是从上一章复制过来再改的，所以**每一章的代码都能单独跑**。想看第五章当时那个"骨架搭好了但还说不出人话"的状态，直接跑 `ch05/` 就行，不用翻 git。

（不用 git 分支，是因为一本书里十一条分支比十一个目录更难管理，读者也更难上手。）

代价是十一份副本会漂移——改一处 bug 要改十一处。所以配两个小工具兜底：一个脚本检查「第 N 章里本章没改动的文件，和第 N-1 章逐字节相同」，一个冒烟脚本把十一章的入口全跑一遍。

（代码主要是AI写的）



## 怎么读这本书

**边读边跑。** 每一章的开头都有一个「本章代码」方框，写清楚这一章要造什么、跑出什么、拿什么对拍。建议读完那个方框就先把代码跑起来，再往下读。

**跟着那张图走。** 第一章会给出一张总览图，把整个推理流程画成四个盒子：Tokenizer、LLM、Sampler、Detokenizer。后面每一章都对应图上的一个框，章首会告诉你现在在哪。

**盯着「引擎」那一行。** 从第四章起，每章开头都有一行当前的引擎形态，比如：

```
第五章  ids → embed → [norm → □ → norm → □] × 30 → norm → lm_head → logits
第八章  ids → embed → [norm → attn → norm → ffn] × 30 → norm → lm_head → logits
```

方框逐章填满。看着它长大，比看架构图有用。



## 写作方式

这本书是我和 AI（Claude Code）一起写的。我提供思路、把握方向，AI 写代码、补细节。具体怎么配合还在摸索，边写边看。

既然说了，就得回答一个问题：**AI 写的代码，凭什么信？**

答案就是上面「阅读约定」的第二条——**代码可不可信，不取决于谁写的**。这本书里每一章的实现都要和 HuggingFace transformers 对拍，判据白纸黑字写在每章开头。不是让你信我，是让你自己验。

某种意义上，这也是这本书能成立的前提：有一个现成的、公认正确的参考实现在旁边，才敢说"从零手写"。



## 本书结构

十二章，分成两段。

**第一段·跑通**——沿着数据流从左走到右，每章造一个部件：

| 章 | 内容 |
|---|---|
| 一 | LLM推理引擎概览：先用别人的引擎跑起来，看到终点 |
| 二 | 模型文件与权重：272 个张量、134,515,008 个参数 |
| 三 | 分词：全书唯一不碰权重的一章 |
| 四 | 词嵌入：一个矩阵读两遍，得到一个零层的 LLM |
| 五 | 归一化：RMSNorm，以及 pre-norm 与 post-norm |
| 六 | 注意力机制：唯一让 token 互相交换信息的部件 |
| 七 | 位置编码：补上 RoPE，注意力才算完整 |
| 八 | 前馈网络：SwiGLU，顺带看一眼 MoE |
| 九 | 残差连接：把两个子层包起来，Block 至此完整 |
| 十 | 采样：接上生成循环，引擎能用了 |

**第二段·跑快**——不改变数据流，改变执行方式：

| 章 | 内容 |
|---|---|
| 十一 | KV Cache：prefill 与 decode，「引擎」二字从这里名副其实 |
| 十二 | FlashAttention：在线 softmax 与分块 |

**后记**：GPU、量化、批处理、vLLM 与 llama.cpp——以及前面承诺过的「然后再去学训练」那条路。
