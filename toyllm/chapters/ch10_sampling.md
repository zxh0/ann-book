# 采样（Sampling）

> **本章代码**：造 Sampler，并把总览图上那条 `append to` 虚线真正接上。
>
> - **造哪个框**：`samp.png` 的 Sampler，以及绕回 Token IDs 的那条虚线
> - **形状**：`(49152,)` logits → softmax → `(49152,)` 概率 → 抽一个 → `(1,)` token id
> - **引擎**：**第一次成为一个循环**——生成、追加、再生成，直到 EOS 或 max_tokens。到这里引擎算是能用了
> - **关键**：这是整条流水线**唯一有随机性**的地方。从 token ids 到 logits 全程是确定性函数，模型每次说的话不一样，全部的「不一样」都发生在这个盒子里
> - **跑出什么**：同 prompt 同种子跑两次结果完全相同；温度从 0 调到 1.5，看输出从复读机滑向胡话
> - **对拍**：三个 filter 与 HF 的 `TemperatureLogitsWarper` / `TopKLogitsWarper` / `TopPLogitsWarper` `torch.equal`；抽样本身用固定种子 + 频率收敛验证
> - **坑**：顺序必须是 temperature → top-k → top-p（温度会改变**哪些词能入选**，不只是改概率）；top-p 要保留跨过阈值的那个边界 token；流式输出要缓冲字节——第三章埋的雷在这里响

上一章结束时，引擎能算出 logits 了，但只会取最大值，而且一次只吐一个 token 就停了。

这一章造采样器，并且把第一章总览图上那条 `append to` 虚线真正接起来——**引擎从这一章开始，从一条流水线变成一个循环。**

红箭头指着 Sampler。LLM 输出的 logits 是 49152 个实数，采样器负责从中挑出一个 token id。

**这是整条流水线上唯一有随机性的地方。** 从 token ids 到 logits，全程是一个确定性函数——同样的输入永远得到同样的 logits。模型每次说的话不一样，全部的"不一样"都发生在这个盒子里。

要讲的几点：

- **两步**：softmax 把 logits 变成概率分布，然后按概率抽一个。
- **温度（temperature）**：softmax 之前先把 logits 除以 T。T 小分布变尖（保守），T 大分布变平（放飞）。T = 0 是极限情况，退化成直接取最大值，也就是 greedy。
- **top-k / top-p**：抽之前先砍掉长尾。top-k 只留分数最高的 k 个；top-p 只留累计概率到 p 为止的那一撮。
- 图里 Sampling 后面那个虚线框是循环的起点——抽出来的 token id 顺着虚线回到最开头。



## 采样

### greedy 的问题

上一章用的是 greedy：取 logits 最大的那个词。它有两个毛病。

**确定性。** 同一个 prompt 永远得到同一个输出，一个字都不会变。作为验证手段这很好（上一章正是靠它做逐字节对拍），作为产品就不行了。

**容易复读。** 一旦进入某个高概率的循环——「的的的」「非常非常非常」——就再也出不来，因为每一步的最大值都指向同一个地方。

还有一个不那么直觉的点值得说：**逐步取最大，不等于整句最优。** 当前这一步概率第二高的词，可能通向一条整体好得多的路。逐步贪心看不到那么远。

### 两步走

所以要采样：按概率分布随机抽一个。

```
logits (49152,) --softmax--> 概率 (49152,) --抽样--> token id
```

softmax 就是先取 exp 再归一化。实现上有个标准做法：**先减去最大值再取 exp**。数学上等价（分子分母同时缩放），但能避免 exp 溢出。

### 唯一的随机性

这一点值得单独强调：**这是整条流水线上唯一有随机性的地方。**

从 token ids 到 logits，全程是一个纯确定性函数——同样的输入，永远得到同样的 logits，一个 bit 都不差（上一章刚验证过）。模型每次说的话不一样，**全部的"不一样"都发生在这个盒子里。**

理解了这一点，很多事情就顺了：为什么固定随机种子就能复现输出；为什么 `temperature=0` 时模型变得完全可预测；为什么调"创造力"其实是在调这个盒子，而不是在调模型。

### filter 和抽样是两回事

温度、top-k、top-p 经常被统称为"采样参数"，但它们**不是抽法**，而是**抽之前先改分布的形状**。

```
logits → [温度] → [top-k] → [top-p] → softmax → 抽
```

真正的"抽"只有一步，就是按概率随机取。前面三个都是预处理。分清这一点，后面的实现会清爽很多。



## 温度

### 做法

softmax 之前，把 logits 除以 $T$ ：

$$p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

### 直觉

- $T < 1$ ：logits 之间的差距被**放大**，分布变尖，模型更保守、更容易选高概率词
- $T > 1$ ：差距被**压平**，分布变平，冷门词也有机会

两个极限：

- $T \to 0$ ：分布退化成 one-hot，等价于 greedy。**注意实现上不能真的除以 0**，要在 $T = 0$ 时直接走 greedy 分支——这是数学上的极限，不是除零异常
- $T \to \infty$ ：退化成均匀分布，完全随机

### 演示

同一个 prompt， $T$ 取 0 / 0.3 / 0.7 / 1.0 / 1.5 各跑一遍，把五段输出并排贴出来。读者会很直观地看到输出从"复读机"一路滑向"胡言乱语"，中间那一档才是可用的。

### 为什么温度必须最先做

因为它改变的是 logits 之间的**相对差距**，而 top-k / top-p 是按差距来筛选候选词的。

顺序错了，后果不是"概率略有不同"，而是**候选集本身就不同**了。这是下面那个"顺序坑"的根源。



## top-k

只保留分数最高的 k 个词，其余全部置 $-\infty$ （同因果掩码，置 $-\infty$ 才能在 softmax 后变成 0）。

**它解决的是长尾问题。** 49152 个词里绝大多数概率极小，但架不住数量多——加起来仍然有可观的质量。不截断的话，每一步都有一定几率抽到一个完全离谱的词，而一个离谱的词会把后面整段带偏。

**它的缺点是 k 是固定的，不适应分布形状：**

- 分布很尖时（下一个词几乎确定）， $k = 50$ 会把 49 个明显不该选的词也放进来
- 分布很平时（有很多合理选项）， $k = 50$ 又可能砍掉一些好的候选



## top-p

### 自适应的截断

top-p 又叫**核采样**（Nucleus Sampling），出自 2019 年的论文 *The Curious Case of Neural Text Degeneration*。做法是按概率从大到小累加，累计到 $p$ 为止，剩下的全丢掉。

好处正是补上了 top-k 的短板：**候选集大小是自适应的**。分布尖的时候可能只留 2 个词，分布平的时候留几百个。

top-k 和 top-p 可以叠加使用，先 k 后 p。

### 边界 token 是个坑

一个具体例子：三个词的概率是 0.6 / 0.3 / 0.1， $p = 0.7$ 。**应该留几个？**

- 从大到小累加：0.6 < 0.7，加上第二个变成 0.9 > 0.7，一超过就砍 → 留 **1 个**
- HF 的做法：**升序**排列，从最小的开始移除，直到剩余的累计质量不足 $1-p$ 为止 → 留 **2 个**

两种都"讲得通"，但只有一种和参考实现一致。差别在于**那个跨过阈值的边界 token 到底要不要**——HF 保留它，所以实际的 nucleus 总是略大于 $p$ 。

按第一种写法实现，模型照样能生成通顺文本，只是候选集系统性地偏小、输出偏保守。**又一个静默错误**，只有对拍能发现。



## 生成循环

到这里才真正把第一章总览图上那条 `append to` 虚线接上。

### 循环体

```
forward → 取最后一个位置的 logits → filter → 采样 → 追加到 ids → 再来一遍
```

**注意只用最后一个位置的 logits。** 模型输出的是 `(T, 49152)`，每个位置都预测了"它的下一个词"。但生成时前 T-1 个预测都用不上——我们已经知道那些位置的实际词是什么了。（训练时才会全用上，那是另一回事。）

### 停止条件

- **EOS token**：模型自己认为说完了
- **max_new_tokens**：兜底，防止无限生成
- 可选：遇到某个字符串就停（stop sequences）

### 流式输出：第三章埋的雷

生成是一个一个 token 出来的，想做打字机效果就得边生成边输出。

**这里第三章那个坑真的会响**：一个汉字 3 个 UTF-8 字节，可能被切进两个 token，逐 token decode 会打印出 `�`。

必须维护一个字节缓冲：每个 token 解出来的字节先进缓冲，凑齐完整字符再输出，凑不齐就等下一个 token。

这个问题在整段 decode 时完全不存在，只在流式时出现——是典型的"推理特有"的坑。

### base 模型和 instruct 模型

值得点一句：SmolLM2-135M 是 **base 模型**，它只会续写，不会对话。给它「你好」，它会接着编下去，而不是回一句「你好，有什么可以帮你」。

想要对话行为得用 `-Instruct` 版本，并且按 `tokenizer_config.json` 里的 chat template 把 prompt 包装成特定格式（角色标记、特殊 token）。这也解释了第三章那个"没有 post-processor，BOS 加不加由调用方决定"——决定权在这里行使。

### 循环带来的新问题

到这里引擎第一次成为**循环**而不是流水线。而也正是在这里，性能问题第一次露头：

**每生成一个 token，都要把整个序列从头 forward 一遍。**

生成 100 个 token，总计算量是 1+2+…+100 ≈ 5000 个 token 的前向。下一章治这个。



## 代码实现

### 一个设计建议：采样器做成类，别做成 if

很自然的写法是在生成循环里判断：

```
if temperature == 0:  取 argmax
else:                 采样
```

**不建议这样。** 这个判断每生成一个 token 就要执行一次，而答案从头到尾都一样。

更好的做法是把它做成策略对象：

- 统一接口 `Sampler.__call__(logits) -> token_id`
- `GreedySampler` 和 `RandomSampler` 两个实现
- 构造时决定一次：`temperature == 0` 就返回 `GreedySampler`，否则返回 `RandomSampler`
- 生成循环里只有一句 `sampler(logits)`，没有任何分支

好处是生成循环干净，而且以后加新的采样策略（beam search、投机解码）不用动模型代码。第十一章的 KV Cache 会用同样的思路（`NoCache` 空对象），可以在这里先立下这个规矩。

另外：让每个 `RandomSampler` 自带一个 `torch.Generator`，这样固定种子不会污染全局 RNG，也不会被别处的随机操作干扰。可复现性是靠这个保证的。

### 三个 filter 写成纯函数

`apply_temperature` / `apply_top_k` / `apply_top_p`，输入 logits 输出 logits，无状态。好测，好组合，好对拍。

### 对拍

分两部分，因为采样的输出没法逐 token 比。

**filter 部分可以严格比。** 它们是纯函数，和 HF 的 `TemperatureLogitsWarper` / `TopKLogitsWarper` / `TopPLogitsWarper` 逐位相等（`torch.equal`）。上面那个 top-p 边界坑，就是靠这一条抓出来的。

**抽样部分改两条判据：**

1. **可复现**：同一个种子跑两次，结果完全相同
2. **分布正确**：构造一个已知的小分布，抽几万次，统计经验频率，看它是否收敛到目标概率



## 本章小节

这一章造完了 Sampler，引擎第一次能用了：

- **采样**：logits → softmax → 抽。这是整条流水线唯一的随机性来源
- **温度**：改变分布尖锐程度， $T = 0$ 退化成 greedy
- **top-k / top-p**：截断长尾，前者固定数量、后者自适应
- **顺序**：temperature → top-k → top-p，错了会改变候选集
- **生成循环**：append to 那条虚线接上了，加上 EOS、max_tokens 和流式字节缓冲

引擎现在是一个完整的循环，能接收一段文字，一个字一个字地吐出后续。

但它很慢，而且慢得很有规律——每生成一个 token 都要把全部历史重算一遍。下一章治它。
