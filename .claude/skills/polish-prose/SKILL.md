# 润色章节文字（toyllm）

把一章「写得差不多了」的草稿，改成可以印出来的正文。

和两个 lint 技能的分工：`check-formulas`、`check-prose` 是**机械体检**，查的是格式和硬规范；
这个技能是**改写工序**，管的是句子顺不顺、段落之间接不接得上、草稿块怎么并进正文。
凡是 lint 能查出来的，这里不重复造规则，最后跑一遍脚本即可。

## When This Skill Applies

- 作者说「这一章写得差不多了，帮我润色」「这一节顺一遍」
- 某一节需要重写或扩写，作者已经指明是哪一节
- 章节文件里还混着 AI 草稿块、脚手架块、粘贴的对话记录，要整理成成稿

**不适用**：

- 从零起草一章（那是写作，不是润色）
- `notes/`：作者手写，**明确不做 AI 润色**（见仓库根 `CLAUDE.md`）
- 作者只是问问题、让你先读一遍建立理解（这种时候只看不改）

## Scope

**暂时只适用 `books/toyllm/chapters/ch*.md`。**

明确排除：

| 路径 | 原因 |
|---|---|
| `notes/**` | 作者手写，刻意不做 AI 润色，只改被点名的错字 |
| `books/ann4us/**` | 暂不适用。等这套规则在 toyllm 上跑顺了再考虑推广 |
| `chapters/_preface.md` | 作者第一人称，**只增不改写**（见 `books/toyllm/CLAUDE.md`） |
| `chapters/todo.md` | 不是书稿，是待办清单 |
| `code/**`（含 `README.md`、docstring） | 不是书稿。但它是**素材来源**，见下文 |

## 动手之前

1. **读三份规范**：仓库根 `CLAUDE.md`（全书通用）、`books/toyllm/CLAUDE.md`（本书特有）、
   本文件。本书的硬约定（简体中文、中英文之间不加空格、全角引号、不用破折号、
   向量粗体小写矩阵非粗体大写）都在前两份里，润色时一并遵守。
2. **读这一章的代码和 README**：`books/toyllm/code/book/chNN/`。正文里引用的每个数字、
   每段脚本输出都必须来自那里。README 里常常已经把某个 TODO 的答案写好了，
   优先把现成素材并进正文，而不是自己另编一套说法。
3. **跑一遍那章的代码**，核对正文引用的输出是否仍然逐字对得上：

   ```bash
   cd books/toyllm/code
   uv run python book/chNN/xxx.py
   ```

4. **先分区，再动笔**。见下一节。

## 章节文件里的四类内容

toyllm 的章节草稿通常混着四类东西，润色的第一步是把它们分开，并且**在方案里说清楚每一块怎么处理**：

| 类别 | 长相 | 处理方式 |
|---|---|---|
| 作者正文 | 「我们先…然后…」，第一人称，无空格 | 润色的对象 |
| AI 草稿块 | 整段 `>` 引用，中英文之间带空格，破折号多 | **素材，不是书稿**。吸收进正文后删掉，不要直接当正文留下 |
| 脚手架块 | 开头的 `> **本章代码**：…` | 建造契约，**读者永远看不到**。定稿时删，不要为了过 lint 去改它 |
| 粘贴的终端输出或对话记录 | 大段裸文本、`\-` 转义、不自然的换行 | 先判断是否**已经过期**（方案变了但记录没删），过期的直接删，有用的提炼成正文 |

## Steps

1. **分区**：按上表把文件切开，列出每一块的位置和归属。
2. **出方案，先不改**：按小节列出「现在的问题 → 拟改法」，以及每个 TODO 打算怎么填、
   素材从哪来。等作者确认。
3. **逐节改**：一次只改确认过的范围。
4. **跑 lint**：

   ```bash
   cd books/toyllm
   python3 ../../.claude/skills/check-formulas/scripts/check.py chapters/chNN_xxx.md
   python3 ../../.claude/skills/check-prose/scripts/check.py    chapters/chNN_xxx.md
   ```

   脚手架块里的命中**忽略**，不要为了消掉它们去改脚手架。
5. **报告**：逐节说改了什么，一行一条。数字有变动的要单独点出来。

### 占位资料（placeholder）

作者写草稿时，会把**查到的资料**和**AI 的回答**先贴进章节文件里占个位置。
这些东西通常以**引用块**（`>`）或**代码块**的形式出现，一眼就能认出来。

**它们是占位资料，不是书稿。** 润色时的处理是：把有用的内容**吸收进正文**，然后**把原块删掉**。
不要把它们当成正文去润色，也不要因为「改了总比删了保险」就留在那儿。

怎么认（以下特征命中一两条基本就是）：

- 中英文之间带空格（`49152 行 × 576 列`、`占全模型的 21%`），而正文不加空格
- 破折号密集，直引号 `""` 而不是全角引号
- 语气是对着作者说话，不是对着读者说话：「这个观察本身就值得写进书里」
  「要不要在循环后面加一行…这样书里引用输出时不用你手数」
- 自带 `###` 小标题，和正文的小节层级对不上
- 粘贴痕迹：`\-` 这样的转义、莫名其妙的换行、终端里复制出来的对齐空格

**代码块要分辨清楚，不能一刀切。** 章节里的代码块有两种，只有后一种是占位资料：

| 是书稿 | 是占位资料 |
|---|---|
| `code/book/chNN/*.py` 里的真代码 | 示意性的 ASCII 流程图、箭头图 |
| `config.json` / `tokenizer.json` 的真片段 | 单独摆一个算式充当小标题（如 `49152 × 576 = 28,311,552`） |
| 脚本真跑出来的终端输出 | AI 贴的实验结果、排行榜、片段列表 |

判据是**能不能溯源**：能指到具体某个文件、某条命令的，是书稿；指不到的，是占位资料。

**吸收之前必须先核实。** 这些块是「查阅到的资料」和「AI 的回答」，**默认不可信**：

1. **可能已经过期**：草稿里的块反映的往往是旧方案。比如第四章文末那段粘贴记录描述的是
   「随机 ID 冒充 30 层」的旧设计，输出是 `Ġstrugg` 刷屏，而现在的 `engine.py` 是真·零层，
   输出是 `time` 刷屏。两套结论留在同一个文件里会自相矛盾。
2. **数字要跑代码验**：凡是能用 `code/book/chNN/` 跑出来的，跑一遍再写进正文。
3. **外部事实要标不确定**：型号、参数量、别家模型的做法这类查来的事实，核不实的，
   在方案里列出来交给作者定夺，不要默认它对。

核实不了又删不掉的，**在方案里单独列出来问作者**，不要自己决定。

### 只做微调，不动结构（minimal-edit）

**作者要的是微调，不是重写。** 整体结构是作者定的，润色不去改它。

不动的东西：

- 小节的**顺序**和**划分**，不重排、不合并、不拆分、不新增小节
- 段落的**切分**，不把一段拆两段，也不把两段并一段
- 作者的**说法**：比喻、举例、口语、自嘲，哪怕你觉得换个说法更漂亮，也不换
- 已经通顺的句子，**不为了「更好」而改**。看不出毛病就别动

改动的粒度以**词和句内**为主。一句话里改一个词、补一个漏字、调一处标点，是对的；
把一段重写一遍，是错的。

发现结构层面的问题（某节该往前挪、两节内容重复、缺一节），**只报告不动手**，
写进方案里交给作者定。

### 重点关注这五类（five-checks）

润色时主要就找这五类毛病，其余一律放过：

**一、错别字。** 同音字、漏字、多字、口误。

> `高位空间` → `高维空间`；`抢不到哪去` → `强不到哪去`；`一些列词元ID` → `一系列词元ID`；
> `model.safetensor` → `model.safetensors`；`这些，数字词元的顺序就一目了然了` → `这样，…`

**二、疏漏。** 话说了一半，或者该有的东西没有。

> `词嵌入权重矩阵一共576` 漏了「列」；某个概念用了但一直没定义；
> 正文里挂着的 `（TODO，…）` 还没填。

**三、前后不一致。** 同一件事，两处写法不同。要往**已定稿的那一处**看齐，不是往新的看齐。

> 权重共享的英文，本章写 `Weights Tying`，第一章写 `Weight Tying`；
> 词嵌入占比，一处写「大约 20%」，别处写「21.0%」；
> 同一个量，表头叫「模长」，正文叫「长度」。

检查范围不止本章：同一术语、同一数字在前面章节怎么写的，`grep` 一遍再定。

**四、前后矛盾。** 不只是写法不同，是两处**说法打架**，必有一处是错的。

> 上文说「一二三四」的顺序维是 1000/2000/3000/4000，下一句却写 two 对应
> `(11355,1500,-2000)`，符号和数值都对不上；
> 正文说投影矩阵是 `[576 × 49152]`，草稿块说「形状和词嵌入表一模一样」（49152 × 576）。

矛盾要**指出是哪一处错**，不要含糊地把两边都改成模棱两可的说法。

**五、不严谨。** 话不算错，但经不起推敲，或者张冠李戴。

> 「这里 `@` 是 Numpy 库提供的」，实际全书用的是 PyTorch，而 `@` 是 Python 的运算符；
> 「前一章写好的 `Weights` 类」，实际是第二章写的；
> 「第二章的脚本 `tokenize_demo.py`」，实际是第三章的脚本；
> 查来的外部事实（某模型的维度、某家的做法），核不实就不要让它以肯定语气留在正文里。

交叉引用（第几章、哪个脚本、哪张图）是这一类的重灾区，**逐个核对文件再确认**。

### 补充和扩写要有授权（expand-on-request）

上一条说的「只微调」是**默认状态**。有些地方作者是要你补充或者扩写的，但这**必须有明确授权**，
授权只有两个来源：

1. **正文里的标记**：`TODO`、`XXX`、`（TODO，补充）`、`（TODO，展开介绍）`、`待补` 之类
2. **作者在提示词里直接要求**：「把这一节展开讲讲」「这里补一段」

**两个来源都没有，就不要扩写**，哪怕你觉得某一节太单薄、某个概念该交代一下。
想补的地方写进方案里问，不要直接动手。

标记有两种，要分清楚：

| 标记的样子 | 它要的是什么 |
|---|---|
| `（TODO，补充）`、`（TODO，展开介绍）`、`TODO，解释一下argmax函数` | **写正文**。补完把标记删掉 |
| `（TODO，…我的解释对吗？）`、`这里解释的对吗？` | **先回答问题**。作者在问你他的说法对不对，得先在报告里正面答复，再谈怎么改 |

还有一类标记是**作者自己要拍板的事**，不是交给你写的，比如术语二选一
（「长度？模长？」「分数？对数得分？logits？」）。这类**列出利弊交给作者定**，不要替他选。

扩写时守住这几条：

- **先找现成素材，再自己写。** 优先级：这一章的 `code/book/chNN/README.md` 和代码注释 →
  前面章节已有的说法 → 章节里那些占位资料块 → 最后才是自己组织语言。
  作者往往已经把答案写在别处了，扩写常常只是「搬过来改成正文口吻」。
- **填坑，不改坑的形状。** 在标记所在的位置补，不要因为补了这一段就去重排上下文、
  新开小节、或者把相邻段落一并重写。
- **补出来的字要像作者写的**：第一人称「我们」，中英文之间不加空格，不用破折号，
  该口语的地方口语。补完自己读一遍，AI 味重就重写。
- **红线照样管**：数字来自代码，术语不自造，外部事实核不实就不写死。
- **补不出来就说补不出来。** 素材不够、事实核不实、或者这个坑本质上要作者自己定，
  在报告里讲清楚卡在哪，不要为了填满而编。

## 术语约定（本书已定）

作者拍过板的术语写法，润色时直接照用，不要在单章里另起一套。
这一节只收**已定**的，待定的不写进来。

### logits

| 场合 | 写法 |
|---|---|
| 正文默认 | **分数** |
| 首次定义（已在第一章给过） | **分数**（Logits），括号内英文首字母大写，和全书术语格式一致 |
| 指代代码里的变量、张量、HF 的类名 | 反引号小写 `logits`、`TopKLogitsWarper` |

**不用**「对数得分」「对数几率」「逻辑值」。理由：logit 的原义是统计学的
$\log\frac{p}{1-p}$（二分类里 sigmoid 的反函数，中文正经译法是「对数几率」），
但 LLM 出口是多分类 softmax，那里的 logits 只满足 $z_j = \log p_j + C$ ，
$C$ 是任意常数，加个常数概率不变。所以它既不是对数几率，数值本身也没有绝对意义。
用上「对数」二字会招来「为什么是对数」的疑问，而本书承诺不讲推导，答不了也不该答。

选「分数」还因为它和全书的动词连得上：给每个词元打分、取最高分、按分数排序、
砍掉分数低的。第四章和第十章全程都这么说话。

**注意撞车**：注意力那边的 $QK^\top$ 也叫分数（第六章有个小标题就叫「算分数」）。
约定是 **logits 叫「分数」不带限定词，注意力那边一律叫「注意力分数」**。
注意力分数总在注意力的语境里出现，带限定词就不会混；反过来给 logits 加限定词，
第十章满篇都要加，累赘。

**当前状态**：第一章已定稿用「分数（Logits）」；**第二章 L232 裸用了 `Logits`**、
**第十章草稿满篇小写 `logits` 中英混排**，两处待各章润色时按上表统一。

### 向量的 $\|\mathbf{v}\|$

| 场合 | 写法 |
|---|---|
| 正文默认 | **模长** |
| 首次出现（第四章定义 $\|\mathbf{v}\|$ 处） | 「用 $\|\mathbf{v}\|$ 表示某向量的**模长**，也就是这个向量的长度」，一句注解，之后全用模长 |
| 表头、代码注释 | 模长（已经是这么写的） |

**不用**「长度」「范数」。

「长度」在本书里已经是**序列长度**的专名：第六章「计算量随序列长度平方增长」、
第十一章满篇「已生成长度」和 `K: (已生成长度, 3, 64)`、第十二章、第三章的
`model_max_length`、第二章的字节长度。第四章说「向量长度」、第六章说「序列长度」，
隔两章撞在一起，而这两个都是全书的核心量。

还有一层：读者是程序员，**「向量的长度」在编程语境里就是 `len(vec)` = 576**，
也就是维度。而第四章满篇在说 576 维、`(T, 576)`，这个误读几乎必然发生。

「范数」是比「模」更宽的概念，用在这里不准，也不必配英文括号（norm 同理）。
中文数学的标准术语是「向量的模」，「模长」是通行的口语复合词，指向明确，
对怕数学的读者也不比已经在用的「余弦相似度」「点积」更吓人。

**当前状态**：第五章 L83、第四章表头、`vocab_head.py` 的注释和 `README.md` 已经在用
「模长」；**待统一的是第四章正文七处**（L125、L133 两处、L138、L140 两处、L169 两处），
以及**第七章 L108「不改变向量长度」、L127「都保范数」**。


## 红线

补充规则时，下面这些是无论如何不能越的：

- **不改数字。** 正文里的形状、参数量、ID、模长、脚本输出，全部以 `code/book/chNN/` 里
  真跑出来的为准。润色只动文字。确实需要改数字时，先跑代码，并在报告里单独点出来。
- **不改代码块。** 章节里的 Python 代码块是 `code/book/chNN/*.py` 的**节选**，
  不要求逐字一致（`check-prose` 那条「逐字一致」的规则按 `toy_*.py` 文件名分派，
  只管 `ann4us`，不管 toyllm）。本书的惯例是：docstring 压成单行注释，且注释文字
  就是该 docstring 的**第一行**，一字不改；`main()` 和打印用的辅助函数略去；
  版面放不下时收窄缩进（ch02 那块收成了 2 空格，代码里还留了句「纯粹为了书面排版」）。
  要守的是三条：每一行真代码都能在 `.py` 里原样找到、注释等于对应 docstring 的首行、
  数字和输出以真跑出来的为准。**动它之前先跑一遍比对，别凭印象说两边不一致。**
- **不抹掉作者的声音。** 「我懒得重新画了」「如果有机会的话，我可能会写一本…」这类
  口语和自嘲是作者的风格，不要改成规范说明文。
- **不引入 AI 文风。** 不加破折号，不在中英文之间加空格，不用直引号 `""`，
  不把「我们」换成被动句。
- **不动术语。** `SmolLM2` 不是 SmolLM，「本章小结」不是「本章小节」，
  `top-k` / `top_k` 两种写法各有各的地盘。
- **不扩大范围。** 作者点名润色哪一节，就只改那一节。顺手发现别处的问题，
  报告出来，不要顺手改掉。
